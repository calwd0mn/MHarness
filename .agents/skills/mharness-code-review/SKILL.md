# MHarness 代码审查

参考 DSH 的 dsh-code-review 审查方法，按 MHarness 的固定装配架构和当前实现范围裁剪。优先发现影响正确性、数据一致性、工具执行与生命周期的具体缺陷。

## 范围与依据

- 默认只读审查，不修改代码、文档、规格或测试。修复须先获得用户针对修改的同意；审查请求本身不授权修复。不提交 Git，不向外部发布审查意见，除非用户明确要求。
- 从被审查项目根目录解析下述路径，不从技能安装目录解析。先确认根包名称为 `mharness`，再读取用户提供的指令及适用的 `AGENTS.md`；本技能不适用于 DSH 或其他仓库。
- 阅读相关实现、`README.md`、工作区 `package.json`，以及 `openspec/specs/` 中相关规格。涉及未归档变更时，读取相应 `openspec/changes/<change>/` 下的 proposal、design、tasks 和相关增量规格；归档后查找现行规格，不硬编码 change 名称。
- 用规格确定约定，用代码和测试确定当前行为，用任务范围区分已实现与待实现能力。tasks 勾选和说明文档不能替代代码证据。规格之间存在冲突时明确指出冲突，不默选一种解释。
- 当前架构为 React/Vite、Fastify、共享 Zod 协议和 SQLite，后端通过普通 TypeScript 模块固定装配。后续以项目现行设计为准，不引入 DSH 的 Cordis 注册、Loader、`./invariant` 配套包、双 SDK、国际化、Agent Notes 或专属门禁要求。
- 不将超出当前变更的待办能力视为缺陷；不擅自要求自动重试、迟到结果结算、跨进程续跑、完整 token 回放或任意外部工具恰好执行一次。只有当前行为违反适用规格或本次承诺时才报告。

## 建立审查基线

1. 明确审查的是指定文件、未提交变更、提交区间还是 PR。读取 Git 状态并区分已暂存、未暂存和未跟踪文件；未跟踪源码不能被普通 diff 遗漏。
2. PR 审查确认实际 base/head；提交区间使用已确认的引用。若无法取得远端状态，披露本地基线的限制，不声称已核对最新 PR。不重置、暂存或覆盖用户变更。
3. 阅读差异及足够的上下文，追踪变更接口的调用方、实现方、共享 Schema、持久记录和 UI 消费方。检查问题是否由本次变更引入；明确区分既有问题与新增问题。
4. 无指定差异的全项目审查，先按当前实现列出审查范围，优先检查已存在的行为。不把规划文件当作已经交付的代码。

## 按变更涉及的行为检查

只展开受影响的条目，不把下列内容当作每次都必须执行的全量清单。

### 会话与持久化

- 用户消息、新 Turn、持久记录和序号是否在应有的事务中提交；同一会话是否最多有一个活动 Turn；失败回滚是否留下可见的半成品或序号缺口。
- 成功响应、实时通知和后续调度是否以提交成功为前提；历史读取、状态摘要和模型上下文是否来自一致的事实来源。
- 重启恢复是否将遗留活动 Turn 结算为 interrupted、已发出未确认工具结算为 unknown、待审批操作作废；恢复不得意外重新执行工具。核对事务、重复恢复及实际文件重开后的行为。
- 明确 SQLite 连接、服务和后台任务的所有者；错误和关闭路径是否释放资源。避免将单实例存储设计误当作已支持多实例协调。

### 模型与 Turn 驱动

- Session、Turn、Step、Attempt 和工具调用标识是否正确关联；Provider 的结束原因是否由 Adapter 统一映射，并由驱动决定继续或结算。
- 完整 assistant 消息与工具调用是否先保存后派发；参数分片、失败或截断的 Attempt 是否意外触发工具。
- 取消、截断、失败与正常完成是否各自结算；仅展示的部分输出是否被错误加入模型上下文；此前成功提交的消息和配对工具结果是否仍保留。
- 实际模型输入、Prompt、工具定义和生成配置是否可追溯，凭据是否泄漏到持久记录、日志或前端。
- 工具批次的 concludeTurn 意向是否只由成功结果触发；在没有更高优先级中止条件时，是否先结算本批剩余调用再结束，且不额外请求模型。核对步数和其他已配置预算的终止路径。

### 工具治理与审批

- 模型参数是否作为未知输入解析并按对应 Schema 校验；本地 Zod 与导出的 JSON Schema 是否表达相同约束；远端 MCP 输入及工具结果是否按约定校验。
- 副作用、审批策略、工具版本、超时和保留字段是否由受信任配置控制，模型能否通过参数绕过；无效参数是否仍进入审批或派发。
- 审批是否绑定确切工具、定义版本、operationId 和不可变参数；重复同意、过期批准、拒绝后批准、取消后批准是否导致额外执行。
- 沿拒绝和取消路径追到实际工具派发点，检查替代调用入口；审批前效果次数应为零，取得派发资格不等于已经执行。
- 取消与派发是否通过原子状态转换协调；尚未派发是否明确为未执行，已发出未确认是否记为 unknown。不能将超时、连接丢失或无效结果推断成工具没有产生效果。
- 区分 operationId 与模型 callId；同参数的新模型调用不自动合并。幂等能力不能被当作自动重试授权；工具端去重应验证实际效果计数和持久台账。

### SSE 与前端

- 连接生命周期是否独立于 Turn；断开订阅是否错误取消任务，显式取消是否传递到当前请求及后续调度。
- 首帧快照与后续队列的交接是否遗漏或重复记录；持久序号、实时版本、Attempt 身份和 chunk 序号是否各自按协议处理。
- 会话切换、重新订阅、迟到回调和丢失 end 帧是否导致串会话、重复消息、草稿丢失或过早清空。Attempt 结算、持久记录和草稿替换是否遵守协议顺序。
- 页面是否准确表达 waiting、truncated、cancelled、interrupted 和工具结果未知等实际状态；重同步失败时是否错误展示成功或旧审批仍可执行。

## 类型、文档与验证

- TypeScript 禁止 `any`；重点审查不安全断言是否掩盖协议不一致。外部 HTTP、模型、MCP 和持久化数据在相应入口校验，不为已有类型保证的内部值机械增加重复校验。
- 核对新增或变更 API 的中文 JSDoc 是否准确说明调用方所需的失败、返回差异、取消、时序及资源所有权；公共说明留在声明约定处。内部注释仅解释非显而易见的原因、约束和风险，不复述流程。
- 核对 README、共享协议、OpenSpec 与实现涉及的行为是否一致；报告具体差异，不因存在 JSDoc 或静态检查通过就认定文档正确。
- 按变更选择实际存在的脚本。当前可用 `pnpm typecheck`、`pnpm --filter @mharness/server test` 和 `pnpm --filter @mharness/web build`；执行前重新确认 package scripts，不假定以后仍相同。不照搬 DSH 的 change-scope、coverage、doc-sync 或快照命令。
- 测试应能在目标缺陷出现时失败，并检查数据库、响应、帧序列、工具效果或资源释放。并发与超时测试使用可控时序，避免仅依赖睡眠或复述实现。
- 只运行相关检查，记录实际结果和缺口。没有凭据不调用真实 Provider；不连接用户正在使用的数据库或重新录制期望输出。不为审查创建测试或修改文件，除非另获授权。

## 输出发现

- 先给影响最大的发现；每项写清位置、触发条件、具体后果和可核对证据。用最小必要的调用链或复现场景支撑，不凭假设报告问题。
- 区分阻断问题与建议。优先报告可操作的缺陷，避免重复已有发现、机械风格意见和超范围功能建议；自动检查已明确揭示的问题可汇总并说明，不包装成额外语义发现。
- 本地文件引用使用单反引号中的 `@path:line`，路径分隔符使用 `/`，不用本地 Markdown 链接。
- 结尾说明审查范围、实际运行的检查、未验证的关键路径。没有发现时直接说明，并保留验证限制；不把“未发现问题”表述为正确性保证。
