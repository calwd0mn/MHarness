## 批次契约和并发边界

采用 `session.commitStaged(build)` 作为后端入口。同步 `build(firstSeq)` 在同会话写入区内读取当前快照并返回只读的 `SessionAppendInput` 批次。`firstSeq` 用于引用同批摘要等记录。构建函数只准备候选值，网络和取消由调用方在串行区之外处理。沿用现有事件快照规则，拒绝空批次、输入自带 seq、手工写入 seed 标记、无效关联或无效 surface 替换。未绑定暂存能力、当前有并发写入占用或旧前缀检查点失败时拒绝，尚未尝试新事务。返回区分 `committed`（附不可变记录）、`rolled-back`（附原错误）和 `pending-reconciliation`（附待核对原因）。本入口接收已获调用方授权的候选，不接收取消信号。调用方在进入暂存前检查取消。候选交给写入器后完成本次提交与核对，并按持久事实报告技术结果。

| 结局 | SQLite | live Session | 后续写入 |
| --- | --- | --- | --- |
| 已确认提交 | 已提交前缀准确结束于批次之后 | 先安装完整日志和派生状态，再按 seq 发布，每条一次 | 从新前缀末尾分配下一 seq，已提交记录跳过普通缓冲 |
| 已确认回滚 | 旧前缀完整，暂存区间为空 | 不推进游标、替换代数或通知。丢弃候选 | 下一条可复用首 seq。定时、flush 和关闭均不重放此批 |
| 结果待核对 | 等原事务结束，再读一致的持久截点 | 保留旧 live 视图与同一份冻结候选 | 拒绝普通 append 和另一暂存写入，阻止业务请求。显式检查点重核对，冲突或读取失败保持阻塞 |

在调用 `commitStaged` 的同步段取得批次占用，覆盖构建、普通尾批排空、落盘确认和发布。因普通 `append` 是同步 API，竞争调用直接失败，避免为已分配给隐藏批次的位置分配第二条事件。读操作继续返回各自原有视图。SQLite 已确认写入但应用仍待核对时，独立持久历史可以读到已经原子提交的整批，live 快照和通知等到可靠核对后更新。监听器重入沿用拒绝语义，首条回调已能看到完整新快照。写入串行项要等同步的确认处理和发布完成才让后续检查点或关闭推进，避免由 Promise 恢复顺序决定可见性。

优先复用 SessionWriter 现有报告回调。暂存结果待核对时由它通知 AgentManager 已绑定的 `blockStorage`，关闭 `storageOpen`。普通检查点失败也走现有存储故障路径。已确认回滚直接返回调用方结算。现有 `recoverStorage()` 先调用 Session 检查点，待技术核对和持久前缀检查成功才恢复新任务准入。直接调用 `Session.flush()` 可完成底层核对。它不替 Agent 重开准入。写入阻塞期间新编号仍受准入拒绝，已受理编号仍按既有规则去重确认。

8.7 在 pre-step 返回后、追加 `step/start` 和构建请求前检查存储准入。在请求检查点 `session.flush()` 返回后、调用 Adapter 前再次检查准入和取消。检查点可能刚完成核对和发布，这时 Agent 仍须确认恢复，先前准备的请求不能越过存储门。若存储仍未知，运行驱动可报告失败，后续按 8.3 的业务结算处理尚不能写入的终态。8.5 不改 Agent 生产文件或 8.7 的现有测试文件，用独立测试文件验证该组合边界，合并后由两项共同复验 pre-step 路径。
