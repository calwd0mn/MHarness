# Session 模块边界与存储实施计划

本计划用于继续 `agent-harness-prototype`。任务范围以 `tasks.md` 的「模块边界与存储」一行为准。验收依据为 1.17 的样例、`design.md` §1.3、§2.1–§2.3、§8，以及 `agent-execution` 和 `execution-streaming` 的相关场景。1.13 按 2.9 和 6.9 实施，交付会话用例与传输契约，正式 HTTP、SSE 和 Agent 联调由各自后续任务验收。

## 基线

- 1.5、1.16、1.17、1.18、2.9、6.9 已勾选。工作区还有 1.21 的代码、测试和进度更新，以及未跟踪的 `packages/session/src/persistence.ts` 和对应服务端导出。开发前将这些改动作为基线带入工作树，保留来源工作区，不覆盖已有改动。
- `SessionPersistence` 和 `SessionHandle` 已有草稿。当前 SQLite `SessionStore` 和在线入口仍使用旧记录格式，根配置也尚未提供新版数据库路径。现有测试通过只能证明当前基线。
- 2026-11-16 基线使用 Node.js 24.13.0、pnpm 10.32.1。在 PowerShell 7 执行 `pnpm typecheck`、`pnpm --filter @mharness/server test`、`pnpm --filter @mharness/web build` 均通过，共 26 个服务端用例。构建有两条来自 Zod 依赖的 Rollup 注解警告。

## 1.8 的两项验收

1. **接口契约**。对照 §2.1、§2.2 和 1.17，核对 `create/open/stat/list/flush` 与 handle 签名、返回值、元数据、生命周期、取消范围、可区分的所有权冲突及中文 JSDoc。通过类型检查和调用方的替身测试，确认 Session 模块拥有此契约，浏览器入口及依赖链未引用存储实现。这项验收通过即可让 1.9、1.11、1.12 和 1.13 按契约推进，1.8 整项仍待实库验收。
2. **真实持久化**。在 1.9、1.10、1.11、1.14 接通后，重跑下列 SQLite 和跨进程场景。测试使用临时数据库，用故障注入覆盖不确定提交和关闭失败。全部通过后勾选 `tasks.md` 的 1.8，并在计划记录对应测试和命令结果。

| 行为 | 通过条件 |
| --- | --- |
| 访问模式及所有权 | 有写入者时仍能只读打开；只读 append/flush 拒绝，重复写入取得可区分的冲突，其他会话可独立获取写入权。 |
| 元数据与首次提交 | 准备中的 handle 对 stat/list/open 不可见。首次批次在写入 header 后失败，另一连接查不到半成品；原句柄重试后一起看见 header、继承数与事件数。显式空 handle.flush 可落盘空 header；统一 flush 及放弃关闭不使准备中的 header 落盘。 |
| 范围与两种前缀 | 已提交 `0..7`、已接受 `0..9` 时，`read()` 返回 8 条，`read(8, 0)` 返回空数组，`read(0, 10)` 拒绝，内存快照返回 10 条。覆盖非法整数、末尾与越界，读取不触发排空。提交尾批后返回 10 条。 |
| 后续批次与事务核对 | 批次失败完整回滚，游标不推进。确认提交且内容全部一致时报告成功；确认回滚且持有写入权时重试原批次；核对失败、部分匹配或冲突时保持写入阻塞，下一次显式 flush 先核对。首次提交核对同时检查 header 和继承数。重开后验证连续、无重复的事件。 |
| 关闭与统一 flush | 关闭幂等，关闭后所有读写操作拒绝。排空失败仍释放写入权且报告原错误。让两个活跃 writer 失败、第三个成功，验证统一 flush 依次处理三者，`AggregateError` 保留失败会话标识和原错误。 |

## 并行分工与合并顺序

开发经用户同意后，由主代理统筹。开发子代理使用 `gpt-6.1-terra`，事务与锁用高思考度，派生及契约用中思考度。采用仓库内隔离工作树，从同一份现有改动基线开始，按文件职责交付。主代理处理共享入口、应用接线和 `tasks.md`。每项采用 TDD，先运行能暴露缺失行为的测试，再实现并回归。新增或修改的 TypeScript 禁用 `any`，按 `jsdoc-contracts` 核对中文 API JSDoc。

| 分工 | 首批可做事项 | 后续交付与依赖 |
| --- | --- | --- |
| 存储，1.8 接口、1.14、1.9 | 核对持久化接口与替身用例，建立旧库、未知版本和新库隔离测试。 | 接口就绪后实现 `node:sqlite` 事件存储、连续游标、已提交读取、事务及结果核对。任何新版写入口打开既有库前先合入 1.14 的保护。用临时库验证旧文件目录和内容受保护、新格式独立可用。 |
| 所有权与恢复，1.11、1.12 | 按 1.16 实现规范化路径和独立的实例／会话锁文件；按 1.17 用事件样例和 handle 替身验证恢复。 | 1.8 接口就绪后接存储锁，合入 1.9、1.11、1.14 后接启动恢复。验证不同端口争用、不同会话并行、只读观察和进程退出释放；用实库验证异常持久前缀、只读视图、一次原子修复和重复启动。 |
| 内存与 API，1.6、1.13 | 1.5 基础上实现 surface 校验及派生缓存，按 2.9、6.9 并行准备 prompt Schema 和复用 SessionEvent 的传输样例。 | 用 1.8 替身及新版存储验证持久创建与历史读取。覆盖空历史 `cursor=-1`、连续序号、原始毫秒与引用、seed 和替换的原样传输。合并时沿用当前在线路由所用的基线契约，协调新旧定义的导出，等对应任务切换旧路由和 SSE 消费。 |

1. 合入 1.8 接口验收和 1.14 保护后，完成 1.9，并接通 1.11。新版存储路径通过显式配置使用，不迁移用户现有数据库。
2. 1.10 接 1.9 的 handle，验证固定 200ms 窗口、串行排空、在途写入、种子不重复入队、检查点覆盖和失败保序重试。合入 1.6 对核心的改动后统一接 `Session.flush()`。在满足 1.9、1.11、1.14 后接 1.12 启动恢复，并执行 1.8 的全部实库用例。
3. 主代理先盘点 1.19 的旧包消费者。1.5、1.8 接口及 1.13 传输边界稳定后，确认剩余定义归属与消费者引用，移除旧 protocol 包及对应依赖。沿类型和运行时两条依赖链检查浏览器无 Fastify、SQLite、Node.js 资源或服务端实现，同步 README 和设计中的模块图及目录示意。边界验收可与实库回归并行，最终分别记录证据。

## 实施和验收记录

- **1.8 接口契约**。实际 SQLite 后端继承 `SessionPersistence`，句柄实现 `SessionHandle`。核对 design §2.1 的签名、访问模式、空会话、取消和关闭约定，运行严格类型检查，使用持久化替身验证创建、已提交历史和失败时的资源释放。中文 JSDoc 已对照实现人工核对。
- **1.8 真实持久化、1.9–1.11、1.14**。SQLite 和独立进程测试验证了 8 条已提交与 10 条已接受的前缀、分支首批回滚和原子发布、事务结果核对阻塞、严格读取、关闭失败仍释放所有权、统一 flush 汇总、受理事件跨批持久及重开后的自有请求编号。故障注入使用隔离临时库。无版本和未知版本库的测试文件内容逐字节保持原样。不同端口的第二个后端在恢复和监听前被拒绝，接替进程可在持有者退出后恢复。
- **1.6、1.12、1.13**。测试覆盖 surface 替换范围、来源、工具配对、重放和派生数组所有权；使用真实写句柄提交工具和 Turn 的中断修复，验证只读临时视图、原始历史与重启幂等。新版 HTTP 创建和历史按原始事件联验，默认启动使用旧版开发接口。后续的正式 prompt 命令、审批答复及 SSE 仍按对应任务接线。
- **1.19**。确认旧 protocol 包的审批定义没有消费者，移除四个包文件和锁文件 importer。运行浏览器入口单独打包及无 Node 类型的编译依赖清单检查，Session 源文件仅涉及公开 API Schema 和 `events.ts`，依赖 Zod。前端构建出现两条现有的 Zod 注解警告。
- PowerShell 7 验证通过 `pnpm install --frozen-lockfile --offline`、`pnpm typecheck`、`pnpm --filter @mharness/server test`（59 项）、`pnpm --filter @mharness/web build` 和 `git diff --check`。待 `continue-review` 交由独立审查代理。
